## 1. 项目概述

RunWise Web 端是微信小程序「RunWise」的配套桌面端应用，面向使用 RunWise 进行跑步训练的普通跑者用户，与小程序共享同一套后端服务与账号体系：高频轻量操作（每日打卡、随手提问）留在小程序完成，Web 端则提供更适合大屏场景的体验——打卡记录的浏览与管理、与「RunWise 助手」的 AI 答疑对话、周/月维度的训练数据可视化，以及一个品牌化的海报式首页。视觉上，Web 端采用「女神异闻录（P5）」红黑撞色海报风作为独立设计语言（切角卡片、米色胶带贴纸、跑者剪影、错位投影标题），以已定稿的首页打样图为基准，向全站五张页面复用收敛；后端由开发者自行负责，Web 前端开发期全部使用 mock 数据，并通过统一开关实现与真实接口的无缝切换。

**功能边界说明**：打样图四宫格中的「训练计划」「伤痛预防」属于小程序端核心功能，Web 端本期不建对应页面，首页仅作入口引导（见第 4 章）。Web 端本期交付 5 个页面：登录 / 首页 / 打卡 / 答疑 / 统计。

## 2. 技术栈与目录结构

### 2.1 技术选型

| 类别 | 选型                                        | 说明                                                                                |
| ---- | ------------------------------------------- | ----------------------------------------------------------------------------------- |
| 框架 | Vue 3（Composition API + `<script setup>`） | 与小程序端（uni-app + Vue3）技术同构，心智复用                                      |
| 构建 | Vite 5                                      | 启动快、env 变量机制成熟（`VITE_*`）                                                |
| 路由 | Vue Router 4（history 模式）                | `meta.requiresAuth` + 全局守卫做访问控制                                            |
| 状态 | Pinia                                       | 仅两个 store：user（登录态）、checkin（打卡数据）                                   |
| 请求 | Axios                                       | 统一封装拦截器，mock 与真实请求共用同一 api 层签名                                  |
| 图表 | ECharts 5（按需引入）                       | 仅柱状图 + 折线图，严格控制体积（见第 9 章）                                        |
| 样式 | 原生 CSS + CSS 变量                         | **不引入任何 UI 框架**：P5 强定制风格下组件库收益为负，视觉还原全靠自研三件套效果类 |
| 语言 | JavaScript                                  | 以给定目录树为基准；第 5 章的 TS 风格结构仅作为数据契约文档，不引入 TS 编译链       |

### 3.2 三件套效果实现方案

**① 切角卡片（P5Card 核心）**

```css

.p5-card {
  position: relative;
  background: var(--p5-panel);
  clip-path: polygon(
    0 0,
    calc(100% - var(--cut)) 0,
    100% var(--cut),
    100% 100%,
    var(--cut) 100%,
    0 calc(100% - var(--cut))
  );
}

/* clip-path 会裁掉 box-shadow，投影挂到外层容器用 drop-shadow */
.has-card-shadow {

/* 右下红色三角角标：打样图四宫格的标志性收尾 */
```

### 3.3 风格浓度分级表

P5 海报风的克制比放开更难。全站按五个浓度档执行，胶带使用数量是硬约束：

| 浓度档 | 页面 / 元素                | 视觉强度 | 边界说明                                                                 |
| ------ | -------------------------- | -------- | ------------------------------------------------------------------------ |
| 全开   | 首页 Hero 区               | ★★★★★    | 错位投影大标题、跑者剪影、赛道弧线、红色几何飞溅全部放开                 |
| 放得开 | 登录页、首页四宫格         | ★★★★     | 切角 + 胶带 + 红色角标齐全，胶带允许大角度（-8° 至 -4°）                 |
| 适中   | NavBar、数据条、统计页     | ★★★      | 结构清晰优先：红黑配色 + 局部切角，胶带 ≤2 处，图表内部不用效果          |
| 克制   | 打卡页、答疑页             | ★★       | 内容可读性优先：仅容器切角与小型 TapeTag（分类标签），禁止大面积红色几何 |
| 极简   | 表单控件、表格、图表坐标区 | ★        | 标准输入框与坐标轴，仅主色点缀选中态 / 激活态                            |

## 4. 页面与组件职责

### 4.1 全局组件

**NavBar.vue（layout）**

- 职责：顶部斜切黑色导航条，右侧入口以红色斜块作为激活态；展示当前用户昵称与退出入口。
- 菜单与映射：首页 `/home`、打卡记录 `/checkin`、AI 答疑 `/qa`、数据统计 `/stats`。
- 说明：打样图导航中的「训练计划 / 打练记录」为小程序端功能，Web 端不设对应路由，导航按实际路由收敛为以上四项（此为设计统筹决策，打样图仅取其视觉形态）。

### 5.3 checkin.js 的 90 天生成算法（保证连续天数逻辑可算出）

以「运行当天」为锚点，生成 [今天 − 89 天， 今天] 共 90 天：

1. **随机断点**：以固定种子从 {今天 − 5、今天 − 6、今天 − 7} 中随机取一天设为**强制休息日 R**（避免连续天数与滚动打卡数恒定不变）；
2. **连续段**：R 的次日（R + 1）至今天**强制打卡** → `streakDays` 为 5~7 的浮动值（断点越靠近今天，数值越小）；
3. 本周一至今天中，除 R 外**同样强制打卡** → 本周除休息日外全勤（若 R 落在本周，自然周打卡次数 = 已过天数 − 1，否则 = 已过天数）；
4. 其余日期以 55% 概率随机打卡（与上述规则取并集，不冲突）；
5. **固定随机种子**：以 `'runwise-' + 日期字符串` 做 hash 种子 → 同一天多次刷新数据完全一致，演示稳定；
6. 字段随机规则：`distanceKm` 取 3.0~10.0（一位小数）；`durationMin` = round(distanceKm × paceMin)，paceMin 在 5.2~7.5 随机；`pace` 由 `formatPace` 推导；`mood` 加权随机（great 20% / good 55% / tired 25%）；30% 的记录带 `note`（从 8 条预设文案池取）。

**下界保证**：连续段（≥ 5 天）整体位于近 7 天滚动窗口内，故任意一天访问均有 `checkinCount ≥ streakDays ≥ 5 > 4`，滚动打卡数不再恒定。

### 5.4 统计口径说明（重要）

- `streakDays`：以今天为终点的连续打卡天数，由随机断点决定，为 5~7 的浮动值（固定种子保证同一天内稳定）。
- `checkinCount` 采用**近 7 天滚动口径**而非自然周：「本周 ≥4 次」在周一、周二物理上不可能成立（已过天数不足 4 天），统一滚动口径后任何一天访问都满足 ≥4（连续段 ≥5 天整体位于滚动窗口内，故恒有 `checkinCount ≥ 5`）；`weekDates` / `distances` 仍为自然周周一至今，未过日期里程为 0。真实接口联调时与后端约定同口径。
- 打样图上的 28.6km / 4 次 / 7 天为视觉占位数字，实际展示以 mock 计算结果为准，不追求与图上数字一一对应。

## 6. 接口层设计

### 6.1 request.js（axios 封装）【v1.3：静默刷新优先】

- `baseURL` 读 `import.meta.env.VITE_API_BASE`，缺省 `/api`；`timeout` 10s。
- **请求拦截器**：从 `stores/user`（兜底 localStorage）读 **accessToken**，自动追加 `Authorization: Bearer <accessToken>`；无 token 不带该头。
- **响应拦截器（401 处理：先刷新、失败才踢回）**——移植小程序 `request.ts` 已验证的刷新队列模式：
  1. 收到 HTTP 401 且非 `/auth/refresh` 自身请求 → 用 refreshToken 调 `auth.refreshToken()`；
  2. **并发排队**：刷新进行中时，后续 401 请求挂起等待，刷新成功后携带新 accessToken **重放原请求**（不丢请求、不重复刷新）；
  3. 刷新成功 → 更新 store 中双 token，队列中的挂起请求依次重放；
  4. 刷新失败（refreshToken 过期 / 后端拒绝）→ `userStore.reset()` 清双 token → 跳 `/login?redirect=当前 fullPath` → 统一提示「登录已过期」。
- **其余响应处理**：业务码非成功 → reject 并统一 toast（约定 `res.data.code === 200` 为成功，联调期与后端核对）；网络错误 → 统一错误提示，reject 透传。
- 开发期 mock 分支不经过 axios：双 token 存取与刷新队列在 M2 通过「手动篡改 localStorage 中的 accessToken 模拟过期」验证，真实生效在联调期。

### 6.2 mock 开关（组件层无感知）

```
VITE_USE_MOCK = true | false
```

- `mock/index.js` 导出常量 `USE_MOCK`；
- 每个 api 函数内部第一行分支：`USE_MOCK` 为真 → 返回对应 mock 函数（带 delay 模拟网络）；为假 → 走 axios 实例；
- 组件与 store 只 import api 函数，**永远不感知数据来源**；切换环境只改 env 文件，零改业务代码。

### router.beforeEach 全局守卫判断逻辑

1. 读取 `userStore.isLoggedIn()`：开发期只判 token 存在性（localStorage 有值即视为已登录，不校验过期）；
2. 若 `to.meta.requiresAuth !== false` 且未登录 → `next({ path: '/login', query: { redirect: to.fullPath } })`，登录成功后回跳原目标；
3. 若 `to.path === '/login'` 且已登录 → `next('/home')`；
4. 其余情况一律放行；
5. 401 兜底与守卫共用同一个 `userStore.reset()`，保证「响应拦截踢出」与「守卫拦截」状态一致，不会出现半登录态。

## 9. 风险与注意事项

**① 跑者剪影图的抠图与压缩（WebP）**
素材从打样图裁切跑者区域，用 remove.bg 或 PS「选择主体 + 选择并遮住」抠透明底；注意去除边缘红色溢色，避免深色底上出现白边 / 红边光晕。导出 PNG 后经 Squoosh 转 WebP（有损 quality ≈ 80，宽控制在 800px 内，目标 <100KB），模板中用 `<picture>` 提供 PNG 兜底。直出 PNG 可能超过 500KB，禁止直接上线。若抠图质量不达标，备选方案为购买 / 自绘 SVG 剪影，不阻塞 M6。

**② iOS Safari 上 clip-path 兼容性**
切角与胶带锯齿均依赖 clip-path：统一只使用 `polygon`（百分比 + calc），禁用旧 iOS 不支持的 `clip-path: path()`；构建链补 `-webkit-clip-path` 前缀以覆盖老版本 Safari。提供 `@supports` 降级路径：不支持时退化为直角卡片 + 伪元素红色角标、胶带退化为直边。真机验收至少覆盖 iOS Safari 16 与微信内置浏览器，重点过首页与打卡页。

**③ ECharts 按需引入减小体积**
只从 `echarts/core` 注册 BarChart、LineChart、Grid / Tooltip / Legend 组件与 CanvasRenderer，禁止全量引入（全量约 1MB）。注册逻辑集中在 StatsChart.vue；组件卸载与数据重置时 `dispose()`，防止 iOS WebView 内存泄漏；构建后用可视化体积分析复核图表增量（目标见 M5）。

**④ 字体版权与加载**
Bebas Neue 为 OFL 开源可商用，但必须自托管（Google Fonts 外链有网络可达性风险），只打包 latin 子集 woff2（约 20KB）；中文一律系统字体栈；`font-display: swap` 防止数字区域长时间空白闪烁。

**⑤ mock 与真实接口的一致性**
第 5 章结构定义即前后端契约，后端建表与 VO 字段命名须与其对齐；日期一律 `'YYYY-MM-DD'` 字符串，避免时区偏移；api 函数签名是联调边界，切换 mock 不允许改动组件层与 store 层代码。

**⑥ 高对比海报风的可读性**
红色仅用于强调（标题投影 / 按钮 / 角标 / 激活态），正文一律白 / 米色，满足 WCAG AA 对比度；深红 hover 态需与主红拉开明度；大面积红黑渐变在低品质屏幕易出现色带，可叠加细噪点纹理 CSS 缓解。

**⑦ token 存储安全**
开发期 token 存 localStorage 可接受（存在 XSS 风险）；token 读写集中收口在 `stores/user.js` 与 `request.js` 两处，后端若提供 httpOnly Cookie 方案，仅需改这两处即可迁移，不动业务代码。

**⑧ AI 答疑链路的降级与演进（v1.2）**
当前后端为 LLM 直连（DashScope，30s 同步超时），RAG 服务化后链路变长（检索 + 生成），需约定：RAG 服务异常时自动降级 LLM 直连，响应结构 `{answer, sources, safetyTip}` 两种模式下完全一致，前端按同一契约渲染；ask 为同步接口，前端 loading 态必须有超时兜底（超过 30s 提示重试）；SSE 流式输出作为后续增强，届时 api 层新增 `askQuestionStream` 而非改动现有签名，聊天组件按特性开关渐进切换。

**⑨ 登录体系与双端互通（v1.3，联调前需后端完成）**
双端方案为「账号统一、方式各宜」：小程序保持微信静默登录（openid 体系，零改动），Web 端账密登录，用户在小程序「我的 → 设置账密」后 `openid` 与 `username` 绑定同一条 User 记录，两端以同一 `userId` 读写打卡 / 答疑 / 统计数据，天然互通。联调前需后端完成 4 项小改动（均不阻塞前端 mock 开发）：

| #   | 改动                                                                                                   | 目的                                                                                                                                                                |
| --- | ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1   | `User` 表增加 `username`（唯一索引）、`password`（BCrypt）两列                                         | Web 账密登录的账号载体，openid 登录路径零改动                                                                                                                       |
| 2   | 新增 `POST /api/auth/login-password`                                                                   | Web 登录接口，返回现有 `LoginVO` 双 token 结构                                                                                                                      |
| 3   | 新增 `POST /api/user/set-password`                                                                     | 小程序内登录态下设置 / 修改账密（绑定动作）                                                                                                                         |
| 4   | JWT claims 增加 `device` 字段，Redis key 改为 `runwise:token:{userId}:{device}:access`（refresh 同理） | **双端同时在线**：当前实现为单 key 覆盖式（`JwtInterceptor` 严格比对 Redis 值），后登录端会挤掉先登录端且 refreshToken 一并失效；加设备维度后两端独立刷新、独立登出 |

边界说明：从未设置账密的纯微信用户无法登录 Web 端（无跨端凭证），属合理限制，登录页给引导文案即可；「小程序扫码登录 Web」需微信开放平台企业资质（网站应用），个人开发者不可行，列为远期可选增强。前端侧对应动作已前置到 M2：双 token 契约 + 静默刷新队列，联调时 `VITE_USE_MOCK=false` 即切真实接口，零改动。
